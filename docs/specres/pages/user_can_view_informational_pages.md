## Functional Overview

`PagesController` serves two categories of informational content: named well-known pages (about, privacy, terms, code of conduct, community moderation, contact, FAQ, bounty, post-a-job, tag moderation, report abuse, robots.txt) and arbitrary admin-created pages reachable by slug via `GET /page/:slug` or top-level `GET /:slug`. For named pages the controller looks up a `Page` record by a fixed slug (e.g., "privacy", "code-of-conduct") and falls back to the built-in ERB template when no database record exists. For slug-based pages the controller resolves the slug through the `Page.from_subforem` scope (preferring subforem-scoped records) before falling back to a global lookup. The `Page` model stores content in one of several formats — HTML, Markdown, JSON, CSS, or plain text — and exposes the correct content type via the `template` field. Cache-control headers are set on cacheable actions, and a surrogate-key header is emitted for CDN purging. Access to each page is gated by a per-page feature flag derived from the slug, ensuring administrators can disable individual pages without a deployment.

## Design Intent

Named page routes (e.g., `/about`, `/privacy`) exist as explicit controller actions rather than all flowing through the generic slug-based `show` action so that each can fall back gracefully to a static ERB template when no corresponding `Page` record has been created in the database. This means community operators get sensible defaults out of the box without needing to seed any data. The `from_subforem` scope ensures that when a subforem context is active, its overriding page variant takes precedence over the global page, enabling per-subforem content customization.

## Key Members

- `Page#template` — one of `contained`, `full_within_layout`, `nav_bar_included`, `json`, `css`, `txt`; controls both layout and response content type
- `Page#is_top_level_path` — when true, the page is served at `/:slug` rather than `/page/:slug`
- `Page#landing_page` — at most one page may be the landing page; enforced by `ensure_uniqueness_of_landinge_page`
- `Page#feature_flag_name` — computed as `page_<slug>`; used to gate visibility per user

## Scenarios

### Viewing a slug-based page

1. A user requests `GET /page/:slug` or, if the page is top-level, `GET /:slug`.
2. The controller resolves the slug: it first queries pages scoped to the current subforem, then falls back to a global lookup; if no record is found, Rails raises `ActiveRecord::RecordNotFound`.
3. The controller checks whether the page's feature flag is accessible to the current user and raises a not-found error if it is not.
4. For a standard HTML page the `show` template is rendered; for `json`, `css`, or `txt` templates the content is returned with the matching content type instead.

### Viewing a named informational page

1. A user requests a well-known URL such as `/about`, `/privacy`, `/terms`, `/code-of-conduct`, `/contact`, `/faq`, `/security`, `/community-moderation`, or `/tag-moderation`.
2. The controller looks up a `Page` record by the fixed slug associated with that route.
3. If a matching record exists it is assigned to `@page` and the `show` template is rendered; if no record exists the built-in locale-specific ERB template for that page is rendered directly.

### Viewing a page with a hierarchical slug

1. A user requests a URL with up to six path segments, e.g., `/first/second/third`.
2. The router captures individual slug fragments (`slug_0` through `slug_5`) and the controller combines them into a single slash-joined slug string.
3. The combined slug is used to look up the `Page` record; the page is rendered if found.

### Requesting a page in plain-text or JSON format

1. A user requests `GET /:slug.txt` for a page whose template is `txt`.
2. The controller returns the page's processed HTML as a plain-text response.
3. If the requested format is `.txt` but the page's template is not `txt`, the request is treated as not found.
4. For pages with a `json` template the controller returns the raw JSON body with `application/json` content type.

### Submitting a report-abuse prefilled with a URL

1. A user navigates to `/report-abuse`, optionally arriving via a referring page or with a `reported_url` query parameter.
2. The controller extracts the reported URL from the `reported_url` param, the `url` param, or the HTTP `Referer` header (in that priority order).
3. A new `FeedbackMessage` instance is initialized with the resolved URL and the `pages/report_abuse` template is rendered, prefilling the form field.

## Failures / Exceptions

- If no `Page` record matches the requested slug, `Page.find_by!` raises `ActiveRecord::RecordNotFound`, resulting in a 404 response.
- If the page's feature flag is not accessible to the current user, the controller calls `not_found`, also resulting in a 404.
- If a `.txt` format is requested but the page's template is not `txt`, `not_found` is called.
- If a page belongs to a different subforem than the one the request is arriving on, the user is redirected to the correct subforem's URL for that page.
