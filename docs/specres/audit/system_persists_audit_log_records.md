## Functional Overview

The `AuditLog` model persists structured audit trail records for significant system actions. Each record stores a `data` payload describing the action, an optional association to the acting `user`, and categorical metadata via `category` and `slug` fields. The model defines two well-known category string constants — one for moderator audit events and one for admin API audit events — which callers use to tag records by origin. Presence of `data` is enforced as a hard constraint; the user association is explicitly optional to support system-initiated or anonymous actions.

## Key Members

- `MODERATOR_AUDIT_LOG_CATEGORY` — frozen string constant `"moderator.audit.log"` identifying records generated by moderator actions
- `ADMIN_API_AUDIT_LOG_CATEGORY` — frozen string constant `"admin_api.audit.log"` identifying records generated through the admin API
- `data` — required payload attribute describing the audited action (presence validated)
- `user` — optional association to the user who triggered the action

## Scenarios

### Record is saved with valid data and no user

1. A caller constructs an audit log record with a non-empty `data` payload, a `category`, and a `slug`, leaving `user` unset.
2. The system validates the record and finds `data` is present and the missing user association is acceptable.
3. The record is persisted successfully.

### Record is rejected when data is absent

1. A caller attempts to save an audit log record without providing a `data` payload.
2. The system validates the record and finds `data` is blank.
3. Validation fails and the record is not saved.

### Record is associated with an acting user

1. A caller constructs an audit log record with a valid `data` payload and assigns an existing user to the `user` association.
2. The system validates the record; both `data` and the optional user are present.
3. The record is persisted with the user reference intact.

### Moderator action is categorised using the standard constant

1. A moderator-triggered event is recorded by setting `category` to `MODERATOR_AUDIT_LOG_CATEGORY`.
2. The system stores the record under that well-known category string.
3. Downstream queries or reports can filter by the constant to retrieve all moderator audit events.

### Admin API action is categorised using the standard constant

1. An admin API request produces an audit event with `category` set to `ADMIN_API_AUDIT_LOG_CATEGORY`.
2. The system stores the record under that well-known category string.
3. Downstream queries or reports can filter by the constant to retrieve all admin API audit events.

## Failures / Exceptions

- Saving a record without a `data` value raises a validation error and prevents persistence.
